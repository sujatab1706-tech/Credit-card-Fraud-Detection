# Customer Churn Prediction

An end-to-end classic ML project that predicts which telecom customers are about to cancel, using **logistic regression**. It covers the full lifecycle: data cleaning, EDA, a tuned and regularised model, thorough evaluation (ROC, PR, calibration, business-cost threshold, lift, coefficient interpretation), a FastAPI service in Docker, CI, and drift monitoring.

Everything runs on a laptop with free tools. No AWS account is needed; the last section shows how it maps to AWS.

## Step 1: Data

The columns copy the public **IBM Telco Customer Churn** sample: demographics (gender, senior, partner, dependents), services (phone, internet type, six add-ons), account (tenure, contract, billing, payment method, charges) and the label `Churn`. The data is generated by `src/generate_data.py` so the project is reproducible and licence-free; the same code runs on the real Kaggle CSV unchanged.

Churn follows a hidden logistic formula plus an **interaction** (fibre × no tech support × month-to-month) and random noise, so logistic regression can do well but not perfectly. The raw file is deliberately messy like a real export:

| Problem | Fix in `features.clean()` |
|---|---|
| `TotalCharges` is text, blank for new customers | to number, 0 when tenure is 0 |
| 15 duplicated rows | dropped (training only; the API scores every row) |
| `"electronic check "` vs `"Electronic check"` | strip and normalise labels |
| `"No internet service"` duplicates `InternetService == "No"` | collapsed to `"No"` |

**EDA findings:** 25% churn (imbalanced). Month-to-month customers churn at 39% vs 4% on two-year contracts. Churn is highest in the first 6 months, and higher with fibre, electronic cheque and paperless billing; tech support and online security go with staying. Gender makes no difference.

## Step 2: Model

Pipeline: `log1p` + `StandardScaler` on tenure and charges, one-hot (first level dropped, unknown categories ignored) on categories, then `LogisticRegression(solver="saga")`.

5-fold stratified CV on the training split (60%), scored by PR-AUC, over 66 combinations:

| Hyperparameter | Values | Winner |
|---|---|---|
| `C` (inverse regularisation) | 0.001 … 100 (log grid) | 1.0 |
| `l1_ratio` | 0 (L2), 0.5 (elastic net), 1 (L1) | 1.0 (L1, zeroes 4 features) |
| `class_weight` | none, balanced | none |

**Imbalance handling:** `class_weight="balanced"` gave the same PR-AUC but much worse log loss and badly inflated probabilities (mean prediction 40% vs 25% actual). Reweighting doesn't change the ranking, it only shifts scores, so the model keeps honest probabilities and the imbalance is handled by **choosing the threshold** on the validation split.

## Step 3: Evaluation (test set, 1,409 customers, never touched during tuning)

| Model | ROC-AUC | PR-AUC | Precision | Recall | F1 |
|---|---|---|---|---|---|
| Always "stays" | 0.500 | 0.249 | – | 0.000 | 0.000 |
| Rule: month-to-month churns | 0.700 | 0.367 | 0.392 | 0.826 | 0.532 |
| Logistic regression, default, threshold 0.5 | 0.837 | 0.629 | 0.670 | 0.450 | 0.538 |
| Tuned, `class_weight=balanced`, threshold 0.5 | 0.837 | 0.627 | 0.502 | 0.729 | 0.595 |
| **Tuned, threshold 0.29 (final)** | **0.837** | **0.629** | **0.526** | **0.692** | **0.598** |

- **Threshold from business cost.** A retention offer costs $50, a churner is worth $500, and the offer saves 30% of churners who get it. Profit on validation peaks at **0.29** (theory: 50 / 150 ≈ 0.33). On test that campaign earns about **+$13.3k**, vs **−$17.8k** for offering everyone a discount.
- **Calibration.** Expected calibration error 0.019: a customer scored 40% churns about 40% of the time, so the probabilities can be used directly for expected-loss calculations.
- **Lift.** The top 10% of scores churn at 75% (**3.0× lift**); the top 30% hold 67% of all churners.
- **Segments.** ROC-AUC is 0.83–0.84 across gender and senior status (no fairness gap). Recall is near zero for two-year customers because few of them pass the threshold.
- **Honest note.** Tuning barely beat default logistic regression. The real gains came from the threshold and from proper evaluation, which is common for a low-variance linear model on clean tabular data.

**Top coefficients** (odds ratio = exp(coef); categories compare with month-to-month / DSL / bank transfer; numbers are per standard deviation of log value):

| Feature | Odds ratio | Meaning |
|---|---|---|
| Two-year contract | 0.10 | ~90% lower odds of churn |
| One-year contract | 0.26 | ~74% lower |
| Tenure | 0.32 | longer-tenured customers much safer |
| Fibre optic | 2.95 | ~3× the odds |
| Electronic cheque | 2.07 | ~2× the odds |
| Tech support | 0.52 | about half the odds |
| Online security | 0.66 | about a third lower |

`TotalCharges` gets a positive coefficient only because it overlaps with tenure (correlation > 0.8), so read tenure and charges together. These are associations, not causal effects; an A/B test of a tech-support offer would show the real impact.

Plots are written to `results/` by `evaluate.py`: `roc_pr_curves.png`, `calibration.png`, `threshold_tradeoff.png`, `confusion_matrix.png`, `coefficients.png`, `lift_by_decile.png`.

## Step 4: Deploy

```bash
docker build -t churn-api .
docker run -p 8000:8000 churn-api
curl -X POST localhost:8000/predict -H "Content-Type: application/json" -d '{
  "gender":"Female","SeniorCitizen":0,"Partner":"No","Dependents":"No","tenure":3,"PhoneService":"Yes",
  "MultipleLines":"No","InternetService":"Fiber optic","OnlineSecurity":"No","OnlineBackup":"No",
  "DeviceProtection":"No","TechSupport":"No","StreamingTV":"Yes","StreamingMovies":"No",
  "Contract":"Month-to-month","PaperlessBilling":"Yes","PaymentMethod":"Electronic check",
  "MonthlyCharges":89.5,"TotalCharges":268.5}'
```

The response has `churn_probability`, `churn_flag`, a `risk_band` and `top_reasons` (coefficient × feature value, the biggest pushes on this customer's log-odds). Pydantic rejects invalid input with a 422. Every prediction is appended to `logs/predictions.csv` for monitoring.

**CI** (`.github/workflows/churn-ci.yml` at the repo root): runs the tests, regenerates the data and retrains from scratch, fails if test ROC-AUC drops below 0.80, then builds the Docker image and smoke-tests `/health`.

## Step 5: Monitor

Churn labels arrive weeks after a prediction, so live accuracy can't be measured. `monitoring/monitor.py` instead compares the API log with a training-time reference:

- **Flag rate** change greater than 10 points → alert.
- **PSI** per input and on the predicted probability (< 0.10 ok, 0.10–0.25 watch, > 0.25 drift), plus a KS test for numbers.

```bash
python monitoring/simulate_traffic.py --n 300            # normal week: no alerts
python monitoring/simulate_traffic.py --n 300 --drift    # promo brings new fibre customers + 15% price rise
python monitoring/monitor.py
```

The shifted week raises alerts on tenure (PSI 0.80), charges, contract and internet mix, and the score distribution, with the flag rate going from 34% to ~70%. When labels arrive, re-run `evaluate.py` on them and retrain if performance has dropped.

## How this maps to AWS

| Here | AWS equivalent |
|---|---|
| `train.py` + grid search | SageMaker Training job / scikit-learn container, or SageMaker Autopilot as a comparison |
| `models/` | S3 + SageMaker Model Registry |
| FastAPI + Docker | SageMaker real-time endpoint (bring your own container), or ECS Fargate / Lambda behind API Gateway |
| `logs/predictions.csv` | SageMaker Data Capture to S3 |
| `monitor.py` on a schedule | SageMaker Model Monitor (data quality + model quality once labels land), CloudWatch alarms |
| GitHub Actions retrain gate | SageMaker Pipelines with a ROC-AUC condition step |
